# План разработки платформы индивидуальной траектории обучения

Документ подготовлен по результатам анализа технического задания `ТЗ_Платформа_индивидуальная_траектория.docx`.

План разделяет исходные требования ТЗ и рекомендуемые уточнения, необходимые для управляемой разработки.

## 1. Назначение проекта

Платформа предназначена для преподавателей и репетиторов. Она объединяет:

- базу учащихся;
- расписание занятий;
- учебные планы;
- индивидуальные образовательные траектории;
- материалы и домашние задания;
- задания и тестирование;
- анализ прогресса;
- уведомления;
- рекомендации преподавателю;
- административное управление.

В ТЗ основными ролями указаны преподаватель и администратор. Если планируется личный кабинет учащегося, его нужно описать отдельным разделом и включить в отдельный этап.

## 2. Замечания и необходимые уточнения к ТЗ

### 2.1. Границы первой версии

ТЗ охватывает большой набор подсистем: CRM учащихся, календарь, файловое хранилище, тестирование, генерацию вариантов, аналитику и рекомендательную систему. До начала разработки нужно разделить функции на MVP и последующие версии.

Рекомендуемый состав MVP:

- авторизация и роли;
- карточки учащихся;
- предметы и темы;
- расписание;
- фиксация занятий;
- учебные планы;
- простая траектория на основе правил;
- материалы и домашние задания;
- базовые тесты;
- аналитика по учащемуся;
- Telegram-уведомления;
- минимальная административная панель.

### 2.2. Разделы ТЗ

В ТЗ есть отдельный раздел с этапами разработки, но он не заполнен, а перечень этапов приведён только в таблице. Таблицу следует сделать основным содержанием раздела «Этапы разработки».

Раздел о технологическом стеке также требует консолидации: стек приведён на титульной странице и в таблице, а отдельный раздел стека фактически пуст.

### 2.3. Пользователи и доступ

Нужно зафиксировать:

- может ли один учащийся быть связан с несколькими преподавателями;
- может ли преподаватель входить в организацию или учебный центр;
- какие данные видит администратор;
- нужен ли отдельный пользовательский тип «учащийся»;
- какие операции доступны после архивирования учащегося.

Удаление учащегося рекомендуется заменить архивированием, чтобы сохранять историю обучения.

### 2.4. Индивидуальная траектория

В ТЗ описана последовательность «диагностика → обучение → контроль → анализ ошибок → повторение», но не определены формальные правила пересчёта.

Для первой версии следует использовать прозрачные правила:

- результат ниже порога — повторение базовой темы;
- большое количество ошибок — дополнительная практика;
- стабильный высокий результат — переход к следующей теме;
- недостаток практики — увеличение количества заданий.

Каждая рекомендация должна иметь объяснение и возможность ручной корректировки преподавателем. Машинное обучение следует оставить на последующую версию.

### 2.5. Аналитика

До реализации нужно определить формулы для:

- общего прогресса;
- среднего результата;
- результата по теме;
- динамики по периодам;
- посещаемости;
- количества ошибок;
- выполнения домашних заданий.

Также нужно определить, какие попытки учитываются: все, последняя, лучшая или среднее значение.

### 2.6. Тестирование

Нужно уточнить:

- поддерживаемые типы вопросов;
- количество попыток;
- ограничение времени;
- возможность повторного прохождения;
- правила оценивания частично правильных ответов;
- способ проверки текстовых ответов;
- сохранение незавершённой попытки.

Для MVP достаточно одиночного выбора, множественного выбора, числового ответа и текстового ответа с ручной проверкой.

### 2.7. Уведомления

Для Telegram и электронной почты требуется определить:

- способ привязки Telegram;
- настройки каналов пользователем;
- часовой пояс;
- повторную отправку при временной ошибке;
- защиту от дублирования уведомлений;
- журнал доставки.

Фоновые отправки следует выполнять отдельным worker-процессом, а не внутри HTTP-запросов.

### 2.8. Файлы и хранение данных

Локальное хранилище подходит для разработки. Для production следует использовать MinIO или S3-совместимое хранилище.

Нужно определить:

- максимальный размер файла;
- разрешённые типы;
- срок хранения;
- права на скачивание;
- проверку содержимого файлов;
- резервное копирование.

### 2.9. Безопасность и эксплуатация

К требованиям ТЗ следует добавить:

- резервное копирование базы данных;
- журнал действий пользователей;
- управление сессиями и отзыв токенов;
- ограничение частоты запросов;
- безопасное хранение секретов;
- разделение development и production-конфигураций;
- проверку требований законодательства о персональных данных;
- мониторинг ошибок и состояния фоновых задач.

Файл `.env` не должен храниться в Git; в репозитории нужен только `.env.example`.

### 2.10. API и критерии приёмки

Приведённого в ТЗ списка endpoint'ов недостаточно. Для каждого ресурса нужно описать:

- CRUD-операции;
- фильтрацию;
- сортировку;
- пагинацию;
- формат ошибок;
- правила авторизации;
- ограничения входных данных;
- коды ответов.

Для каждого модуля должны быть заранее определены критерии приёмки.

## 3. Этапы разработки

### Этап 0. Уточнение требований и проектирование

Результаты этапа:

- окончательные границы MVP;
- карта ролей и прав;
- пользовательские сценарии преподавателя;
- ER-модель базы данных;
- API-контракт OpenAPI;
- прототипы ключевых экранов;
- формулы аналитики;
- правила построения траектории;
- критерии приёмки.

Ключевые решения, которые должны быть приняты до разработки:

- входит ли учащийся в систему как отдельный пользователь;
- поддерживаются ли организации и несколько преподавателей;
- состав типов тестовых вопросов;
- обязательные каналы уведомлений;
- правила хранения файлов;
- срок хранения данных.

### Этап 1. Базовая инфраструктура

Реализовать:

- React-приложение и маршрутизацию;
- FastAPI-приложение;
- PostgreSQL;
- SQLAlchemy и Alembic;
- Docker Compose;
- конфигурацию окружений;
- базовую структуру frontend и backend;
- OpenAPI-документацию;
- логирование;
- единый формат ошибок;
- базовые CI-проверки.

Результат: проект запускается через Docker, база подключается, миграции выполняются.

### Этап 2. Регистрация, авторизация и права доступа

Реализовать:

- регистрацию и вход;
- JWT access и refresh tokens;
- выход из системы;
- восстановление и смену пароля;
- профиль пользователя;
- роли преподавателя и администратора;
- проверку доступа к объектам;
- ограничение преподавателя собственными учащимися.

Критерий готовности: пользователь не может получить чужие данные через интерфейс или API.

### Этап 3. Учащиеся и учебная информация

Реализовать:

- создание и редактирование карточки учащегося;
- архивирование учащегося;
- контактные и учебные данные;
- цели обучения;
- желаемый результат;
- уровень подготовки;
- комментарии преподавателя;
- историю изменений;
- базовую страницу прогресса.

### Этап 4. Расписание и занятия

Реализовать:

- создание занятия;
- выбор учащегося и предмета;
- дату, время и длительность;
- календарь;
- перенос и отмену;
- повторяющиеся занятия;
- проверку пересечений;
- часовой пояс;
- статусы занятия;
- фиксацию фактически проведённого занятия.

При переносе пользователь должен явно выбирать: изменить только текущее занятие или текущую и последующие записи серии.

### Этап 5. Уведомления

Реализовать:

- привязку Telegram;
- настройки уведомлений;
- напоминания за 60 и 15 минут;
- уведомления о переносе и отмене;
- журнал отправок;
- повторные попытки при временных ошибках;
- защиту от повторной отправки;
- настройки часового пояса.

Email можно подключить после стабилизации Telegram-канала.

### Этап 6. Учебные планы и индивидуальная траектория

Реализовать:

- предметы и темы;
- уровни подготовки;
- учебные планы;
- порядок тем;
- количество занятий;
- контрольные точки;
- личные планы;
- общие планы;
- копирование общего плана в библиотеку преподавателя;
- адаптацию плана под учащегося;
- фиксацию текущего этапа;
- пересчёт траектории по правилам;
- ручное редактирование траектории.

### Этап 7. Проведение занятий, материалы и домашние задания

Реализовать:

- фиксацию изученных тем;
- выполненные задания;
- результаты;
- домашнюю работу;
- комментарии и рекомендации;
- загрузку материалов;
- связь файла с учащимся, занятием и темой;
- ограничения размера и типа файла;
- сроки выполнения домашней работы;
- статусы домашнего задания.

### Этап 8. База заданий и тестирование

Реализовать:

- каталог заданий;
- предмет, тему, класс и сложность;
- правильные ответы;
- одиночный и множественный выбор;
- числовые ответы;
- текстовые ответы с ручной проверкой;
- попытки прохождения;
- подсчёт результата;
- назначение теста учащемуся;
- сохранение результата в истории.

Генерацию вариантов добавлять после появления стабильной базы заданий. В первой версии вариант можно формировать по фильтрам с контролем дублей.

### Этап 9. Аналитика и визуализация

Реализовать:

- общий прогресс;
- средний результат;
- результаты по темам;
- динамику по периодам;
- посещаемость;
- количество ошибок;
- сложность заданий;
- сильные и проблемные темы;
- выполнение домашних заданий;
- графики и диаграммы.

### Этап 10. Рекомендации и корректировка траектории

Реализовать rule-based рекомендации:

- повторить тему;
- увеличить практику;
- изменить сложность;
- провести дополнительный тест;
- вернуться к предыдущей теме;
- перейти к следующему разделу;
- скорректировать учебный план.

Для каждой рекомендации показывать причину. Преподаватель должен иметь возможность принять, отклонить или изменить рекомендацию.

### Этап 11. Административная панель

Реализовать:

- управление пользователями;
- назначение ролей;
- управление предметами и темами;
- управление заданиями;
- модерацию общих учебных планов;
- блокировку пользователей;
- системную статистику;
- просмотр журналов действий и ошибок.

### Этап 12. Интеграционное тестирование и выпуск

Проверить сквозной сценарий:

```text
Создание учащегося
→ первичная диагностика
→ выбор учебного плана
→ формирование траектории
→ создание расписания
→ уведомление
→ проведение занятия
→ выдача материалов и домашнего задания
→ тестирование
→ сохранение результата
→ анализ прогресса
→ рекомендация
→ корректировка траектории
```

Перед выпуском проверить:

- права доступа;
- календарь и повторяющиеся занятия;
- уведомления;
- загрузку и скачивание файлов;
- подсчёт результатов;
- формулы аналитики;
- фоновые задачи;
- миграции базы данных;
- резервное копирование;
- Docker-развёртывание;
- восстановление после ошибки.

Подготовить:

- README для запуска;
- инструкцию администратора;
- инструкцию преподавателя;
- OpenAPI-документацию;
- `.env.example`;
- процедуру резервного копирования;
- список известных ограничений;
- сценарий пилотного запуска.

## 5. Функции, которые лучше отложить

Следующие возможности не должны блокировать первую рабочую версию:

- кабинет учащегося;
- мобильное приложение;
- машинное обучение;
- сложная генерация вариантов;
- расширенные типы вопросов;
- автоматическая проверка свободного текста;
- продвинутая библиотека общих планов;
- несколько организаций и сложная иерархия доступа;
- дополнительные каналы уведомлений.

## 6. Рекомендуемый технологический контур

- Backend: Python, FastAPI, Uvicorn.
- ORM и миграции: SQLAlchemy, Alembic.
- Валидация: Pydantic.
- База данных: PostgreSQL.
- Frontend: React с TypeScript.
- Клиент API: Axios или аналогичный HTTP-клиент.
- Формы: React Hook Form и Zod или эквивалент.
- Графики: Recharts или Chart.js.
- Авторизация: JWT и bcrypt/argon2.
- Фоновые задачи: отдельный worker и планировщик.
- Уведомления: Telegram Bot API и SMTP-провайдер.
- Файлы: MinIO или S3-совместимое хранилище.
- Развёртывание: Docker и Docker Compose.
- Документация API: Swagger/OpenAPI.
- Контроль версий: Git.

## 7. Итоговая архитектурная идея

Центральной сущностью системы является история обучения учащегося. Она связывает занятия, темы, задания, тесты, домашние работы и результаты. На основании этой истории строятся аналитика, рекомендации и индивидуальная траектория.

Сначала должна быть создана надёжная база данных учебного процесса. После этого можно безопасно добавлять автоматические рекомендации и более сложные алгоритмы адаптации.
