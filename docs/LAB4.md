# Лабораторная работа №4 — контейнеризация backend

**Дисциплина:** Разработка серверных приложений.

**Тема:** Контейнеризация серверного приложения с использованием Docker и написание оптимального Dockerfile.

**Проект:** Dailybase — платформа индивидуальной траектории обучения.

**Методичка:** `Lab#04_Docker.pdf` из [папки лабораторных работ](https://drive.google.com/drive/folders/1fwY7O8OnPeHtRFqjpxeAQ4JUWXz45qph).

## 1. Цель и результат

Упаковать backend из ЛР3 вместе с Python и зависимостями в Docker-образ,
запустить контейнер с публикацией порта и настройками окружения,
проверить ответ `GET /api/v1/health`.

Для Python методичка прямо разрешает одноэтапную сборку на базе
`python:3.11-slim` с установкой зависимостей через `pip` и запуском через `CMD`.
Именно этот вариант применён в проекте: отдельного этапа компиляции приложения нет.

## 3. Как устроен Dockerfile

1. `FROM python:3.11-slim` задаёт компактную Linux-среду с Python.
2. `WORKDIR /app` задаёт рабочий каталог.
3. `ENV` отключает запись `.pyc`, включает немедленный вывод Python в логи
   и задаёт сетевые параметры по умолчанию.
4. Сначала копируется только `requirements.txt` и устанавливаются зависимости.
   Изменение кода backend не сбрасывает кэш установки зависимостей.
5. Затем копируется каталог `backend/`. Локальное виртуальное окружение не используется:
   зависимости устанавливаются для Linux внутри образа.
6. `USER appuser` запускает приложение от непривилегированного пользователя.
7. `EXPOSE 8000` документирует порт приложения.
8. `CMD ["python", "-m", "backend.app"]` запускает существующую точку входа ЛР3.

`HTTP_HOST=0.0.0.0` позволяет принимать запросы через сетевой интерфейс контейнера.
Если слушать только `127.0.0.1` внутри контейнера, опубликованный порт не сможет
доставить запрос приложению. На компьютере порт опубликован только на `127.0.0.1`.

`HTTP_PORT=8000` — порт приложения внутри контейнера. `8084` — порт компьютера.
В примере методички используется `8080`; здесь выбран `8084`, чтобы запуск
не пересекался с сервером Swagger-документации ЛР2 на `8080`.
Путь health сохранён из ЛР3: `/api/v1/health`, как и в примере команды curl в методичке.

## 4. Выполнение работы

Нужен запущенный Docker Desktop в режиме Linux containers.
Все команды PowerShell выполняются из корня репозитория.

### Шаг 1. Проверка файлов

```powershell
Get-Content .dockerignore
Get-Content Dockerfile
```

`.dockerignore` действует на контекст сборки, `.gitignore` — на Git.
Это разные механизмы: наличие `.gitignore` само по себе не исключает `.env` из Docker.

### Шаг 2. Сборка образа

```powershell
docker build -t dailybase-backend:lab4 .
docker images dailybase-backend
```

Точка в конце — текущий каталог как контекст сборки.
`dailybase-backend` — имя образа, `lab4` — его тег.

### Шаг 3. Запуск контейнера

```powershell
docker run --name dailybase-lab4 -d -p 127.0.0.1:8084:8000 -e HTTP_HOST=0.0.0.0 -e HTTP_PORT=8000 -e APP_ENV=production dailybase-backend:lab4
docker ps --filter name=dailybase-lab4
```

`-d` запускает контейнер в фоне; `--name` задаёт имя; `-p` публикует порт;
`-e` передаёт переменные окружения. Значение `production` в ответе health
показывает, что приложение получило настройку при запуске.
Переменные читает существующий `Settings` из ЛР3.
Для этой лабораторной `.env` внутри образа не нужен.

### Шаг 4. Проверка приложения

С компьютера через опубликованный порт:

```powershell
curl.exe -i http://127.0.0.1:8084/api/v1/health
```

Ожидается `HTTP/1.1 200 OK`, JSON со `status: "pass"`, именем приложения,
версией, `environment: "production"` и неотрицательным `uptime_seconds`.
Время работы меняется при последующих запросах.

Запрос непосредственно внутри контейнера через стандартную библиотеку Python:

```powershell
docker exec dailybase-lab4 python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/api/v1/health').read().decode())"
```

В браузере доступны:

- [Health](http://127.0.0.1:8084/api/v1/health).
- [Swagger backend](http://127.0.0.1:8084/docs): раскрыть `GET /api/v1/health`, нажать **Try it out**, затем **Execute**.

Логи приложения:

```powershell
docker logs dailybase-lab4
```

В логах должны быть сообщения о запуске Uvicorn и успешном запросе health с кодом `200`.

### Шаг 5. Управление жизненным циклом

```powershell
docker stop dailybase-lab4
docker ps -a --filter name=dailybase-lab4
docker rm dailybase-lab4
```

`stop` останавливает контейнер; `rm` удаляет остановленный контейнер.
Собранный образ остаётся, поэтому контейнер можно снова создать командой из шага 3.
Если контейнер лишь остановлен и ещё не удалён, используйте `docker start dailybase-lab4`.
Повторный `docker run` с занятым именем завершится ошибкой.

## 6. Ответы на контрольные вопросы

### 1. В чём главное отличие виртуальной машины от Docker-контейнера?

Виртуальная машина запускает отдельную гостевую ОС со своим ядром поверх
гипервизора. Контейнер изолирует процессы и их файловую систему, используя
ядро среды, в которой работает Docker Engine. Обычно контейнер запускается
быстрее и требует меньше ресурсов. На Windows наши Linux-контейнеры работают
через Linux-среду Docker Desktop/WSL2, а не напрямую на ядре Windows.

### 2. Зачем нужен .dockerignore и к чему приводит его отсутствие?

Он исключает ненужные файлы из контекста сборки. Без него туда могут попасть
`.env` с секретами, `.git`, локальные зависимости, логи и тесты. Это увеличивает
объём передаваемых данных; при широком `COPY . .` лишние файлы попадут и в образ.
В проекте исключены эти файлы, а `COPY` дополнительно ограничен requirements и backend.

### 3. Что такое многоэтапная сборка и какие преимущества она даёт?

В одном Dockerfile объявляют несколько стадий через `FROM`. В первой собирают
приложение или зависимости; в финальную переносят только необходимый результат
через `COPY --from=builder`. Компиляторы, SDK и временные файлы остаются за пределами
финального образа, уменьшая его размер и число ненужных компонентов.
Для этого Python-проекта методичка разрешает одноэтапный образ `slim`: отдельная
компиляция приложения не требуется. Multi-stage здесь не используется.

### 4. Зачем разделять копирование файлов зависимостей и остального исходного кода?

Docker кэширует результаты инструкций сборки. Если сначала скопировать
`requirements.txt` и установить пакеты, а затем скопировать backend,
изменение только backend позволит переиспользовать слой с зависимостями.
Если сначала выполнить `COPY . .`, изменение кода сбросит кэш последующей установки.
При изменении самого `requirements.txt` зависимости будут установлены заново.

### 5. Чем отличаются EXPOSE и флаг -p?

`EXPOSE 8000` — описание порта приложения в образе; он сам не публикует порт
на компьютере. `-p 127.0.0.1:8084:8000` при запуске создаёт перенаправление:
порт `8084` на loopback-интерфейсе компьютера → порт `8000` контейнера.
Публикация работает и без `EXPOSE`, а приложение должно слушать соответствующий порт.
