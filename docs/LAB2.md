# Лабораторная работа №2 — REST API и OpenAPI

## Результат

Спроектирован контракт платформы индивидуальной траектории обучения: 21 операция для регистрации, входа, профиля, учащихся, занятий и предметов. Для трёх основных ресурсов представлены GET, POST, PUT, PATCH и DELETE. Спецификация использует OpenAPI 3.0.3, JWT Bearer, UUID, схемы запросов и ответов, единый ErrorResponse и переиспользуемые ответы ошибок.

- [Спецификация](../openapi.yaml).
- [Таблица операций и бизнес-правила](../ARCHITECTURE.md#11-rest-api-specs--лабораторная-работа-2).
- [Требования лабораторной](https://drive.google.com/file/d/1b9f8ZBFwL9RSH6tG27yjEKWKbfLFp3MT/view).
- [Стандарт OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html).

Backend в этой работе не реализуется: спецификация описывает будущий интерфейс и не подтверждает выполнение запросов сервером.

## Демонстрация Swagger UI

Из корня репозитория:

```bash
python -m http.server 8080 --bind 127.0.0.1
```

Открыть [Swagger UI](http://127.0.0.1:8080/docs/swagger.html).
Показать группы Auth, Users, Students, Lessons, Subjects и раздел Schemas. Развернуть POST /students, PATCH /lessons/{id} и ErrorResponse.

HTML загружает Swagger UI 5.17.14 из unpkg, поэтому для интерфейса требуется интернет. Спецификация загружается с локального сервера. Отправка запросов отключена, поскольку backend пока отсутствует. Для другой среды можно открыть openapi.yaml в [Swagger Editor](https://editor.swagger.io/) через File → Import file.

## Контрольные вопросы

### 1. Чем отличаются Query, Path и Request Body

Path идентифицирует конкретный ресурс: `/students/{id}`. Такой параметр обязателен и является частью URI.

Query задаёт фильтры и параметры представления коллекции: `/lessons?student_id=...&limit=20&offset=0`. Его используют для поиска, фильтрации, сортировки и пагинации.

Request Body содержит структурированные данные создаваемого или изменяемого объекта. Например, POST /students получает JSON с full_name и goals. Пароль передаётся в теле POST /auth/login по HTTPS, а не в URL. Для GET тело не используется.

### 2. Что такое идемпотентность

Метод идемпотентен, если повтор одинакового запроса имеет тот же предполагаемый эффект на состояние сервера, что и один запрос.

- GET читает состояние и не должен его изменять.
- PUT заменяет ресурс одинаковыми значениями.
- DELETE оставляет ресурс удалённым. Первый запрос может вернуть 204, следующий — 404, но конечное состояние одинаковое.
- POST обычно создаёт новый ресурс при каждом повторе и поэтому не является идемпотентным по общему правилу.

PATCH не гарантирует идемпотентность в общем случае. В нашем контракте установка конкретных значений, например status=archived, спроектирована идемпотентно. Команда «увеличить на один» имела бы другую семантику.

### 3. Когда возвращать 401 и 403

401 означает отсутствие действительных учётных данных: нет JWT, токен неверен или истёк. Ответ содержит WWW-Authenticate: Bearer. Неверные данные входа также дают 401.

403 означает, что пользователь распознан, но операция запрещена. Преподаватель не может создавать общий предмет, поскольку это действие администратора.

Для чужих учащихся и занятий контракт возвращает 404, чтобы не раскрывать существование персональных данных другого преподавателя.

### 4. Зачем components/schemas и $ref

components/schemas хранит именованные модели данных. `$ref` ссылается на такую модель вместо повторного описания.

Например, StudentResponse используется для ответа GET, POST, PUT и PATCH, а ErrorResponse — во всех ошибках. Это уменьшает дублирование, помогает поддерживать единый формат и позволяет инструментам строить документацию и генераторы клиентов.

Схема сама по себе не выполняет проверку в работающем сервере: backend должен реализовать валидацию, соответствующую контракту.

### 5. Чем PUT отличается от PATCH

PUT задаёт полное новое представление изменяемых полей ресурса. В нашем контракте все поля ReplaceRequest обязательны; nullable-поля можно явно очистить через null. id, teacher_id и created_at остаются серверными.

PATCH передаёт только изменяемые поля. Непереданные поля сохраняются, null очищает только nullable-поле, пустой объект запрещён. PATCH /lessons/{id} используется также для переноса и смены статуса по разрешённым переходам.

## Возможные дополнительные вопросы

**Почему 400, хотя FastAPI обычно возвращает 422?** В лабораторной принят 400 для ошибок входных данных. При реализации нужен собственный обработчик RequestValidationError, возвращающий ErrorResponse и статус 400.

**Почему разные CreateRequest, ReplaceRequest, PatchRequest и Response?** Требования различаются: при создании некоторые поля необязательны, при полной замене обязательны, при PATCH нужны только изменения, а ответ содержит серверные поля. Клиент не может подменить владельца через тело запроса.

**Что означает 409?** Запрос формально корректен, но конфликтует с текущим состоянием: email уже занят, занятия пересекаются, запись имеет зависимости или запрошен запрещённый переход статуса.

**Что означает 204?** Успех без тела ответа. Возвращать JSON с этим статусом не следует.

**Почему учащегося лучше архивировать?** PATCH status=archived сохраняет историю. DELETE доступен только без зависимостей; иначе 409.

**OpenAPI и Swagger — одно и то же?** OpenAPI — стандарт контракта. Swagger Editor и Swagger UI — инструменты редактирования и отображения этого контракта.

**Что обеспечивает JWT?** Он передаёт подписанные сведения об аутентификации. Проверки роли, активности учётной записи и принадлежности объекта выполняет backend. Сам токен не обеспечивает эти проверки автоматически.
